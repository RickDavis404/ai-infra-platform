# CNPG Postgres clusters (`langfuse-pg`, `litellm-pg`)

Two independent CloudNativePG `Cluster` resources — Postgres is the authoritative
transactional store and the two apps do **not** share one Postgres instance:

| Cluster       | Namespace       | Database            | Owner     | Bootstrap secret  |
|---------------|-----------------|---------------------|-----------|-------------------|
| `langfuse-pg` | `langfuse-data` | `postgres_langfuse` | `langfuse`| `langfuse-pg-app` |
| `litellm-pg`  | `litellm`       | `litellm`           | `litellm` | `litellm-pg-app`  |

Both clusters are structurally identical aside from namespace, database/owner, and
bootstrap secret name.

## HA shape

- `instances: 3` (one primary + two standbys) per cluster.
- Quorum synchronous replication via `spec.postgresql.synchronous`
  (`method: any`, `number: 1`): a commit is acknowledged only after at least one of
  the two standbys confirms (RPO approximately 0). `number` is kept strictly below
  `instances - 1` (1 < 2) so a single standby outage never stalls writes — which is
  why 3 instances are required rather than 2.
- `primaryUpdateStrategy: unsupervised` — CNPG drives rolling updates and failover.
  On primary loss it promotes a healthy standby automatically (RTO is promotion plus
  service re-point, typically tens of seconds).
- Pod anti-affinity (`enablePodAntiAffinity: true`, `podAntiAffinityType: required`,
  `topologyKey: kubernetes.io/hostname`) spreads all three instances across the three
  k3s nodes.

## Image & storage

- Image `ghcr.io/cloudnative-pg/postgresql:18-system-trixie` (PG 18 GA, Debian
  Trixie, multi-arch). The Alpine variant is intentionally avoided.
- `storageClass: local-path`, `size: 10Gi` per instance (raise to `20Gi` if needed).
  Because `local-path` PVCs are node-pinned, a rescheduled pod loses its PVC and CNPG
  re-clones a fresh replica from the primary onto the new node — 3 instances guarantee
  a re-clone never races against the only surviving copy.

## Resources & metrics

- requests `cpu: 250m, memory: 512Mi`; limits `memory: 1Gi` (CPU left uncapped). This
  moves Postgres out of BestEffort QoS.
- `monitoring.enablePodMonitor: false`; instead `inheritedMetadata.annotations`
  expose `prometheus.io/scrape: "true"` on port `9187` (`/metrics`) so Prometheus
  scrapes each pod directly.
- `timezone: UTC` is set platform-wide; Langfuse specifically requires it.

## Secrets (provided out-of-band; not authored here)

The bootstrap secrets carry `username` + `password` and are generated by the
fnox+age flow (see `secrets/`). CNPG additionally mints a per-cluster `<cluster>-app`
Secret containing a ready-to-use `uri` key (full `postgresql://...` string); the apps
consume that `uri` via `secretKeyRef` for `DATABASE_URL` (no duplicated literal).

| Secret           | Namespace       | Keys (referenced)              |
|------------------|-----------------|--------------------------------|
| `langfuse-pg-app`| `langfuse-data` | `username`, `password`         |
| `litellm-pg-app` | `litellm`       | `username`, `password`         |

CNPG also publishes/augments these with `uri` (and a `-rw` Service routing to the
current primary) once the cluster is bootstrapped.

## Optional Barman PITR

Each CR carries a commented-out `backup.barmanObjectStore` block targeting a SeaweedFS
S3 bucket plus a `ScheduledBackup`. It is off by default; enabling it requires §12.5
SeaweedFS Ready and a dedicated backup bucket, and demonstrates the full PITR loop
against the in-cluster object store.

## Apply

```bash
# Operator first (see kubernetes/operators/cnpg), then:
kubectl apply -k kubernetes/langfuse-data/cnpg
kubectl -n langfuse-data wait --for=condition=Ready cluster/langfuse-pg --timeout=10m
kubectl -n litellm        wait --for=condition=Ready cluster/litellm-pg  --timeout=10m
```

Apps connect via the operator-minted `-rw` Service (current primary) using the
CNPG-generated `uri` secret key.
